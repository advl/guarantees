# AGENTS.md

Instructions for whoever works on this repository. Everything here is true at the commit that carries it.

## Commands

`bun run` is the task face: every gate is a script in `package.json`, and the pipeline runs those scripts and nothing else.

| Command | What it does |
|---|---|
| `bun install` | Installs the toolchain. The lockfile is `bun.lock`; the pipeline installs with `--frozen-lockfile`. |
| `bun run build` | `tsc -p tsconfig.build.json` into `dist/`: modules under `dist/esm`, declarations under `dist/types`; then `build:contract`. |
| `bun run build:contract` | `bun src/scripts/emitSchemas.ts`: one `contract/<name>.schema.json` per schema the `contract` domain declares, written as `JSON.stringify(schema, null, 2)` and a newline into `contract/` under the working directory, or into the directory given as the first argument. |
| `bun run check` | `build`, then `check:biome` (format and lint over `scripts`, `src`, `vitest.config.ts` and the JSON files outside `contract/`), then `check:ts` (`tsc --noEmit` over everything `tsconfig.json` includes), then `check:leakage`, then `check:webarchitect` (the manifest, the biome and TypeScript configuration and the licence against the `library` ruleset), then `check:structure`, then `check:contract`. |
| `bun run check:fix` | The formatter and its safe fixes applied, then the type check. |
| `bun run check:contract` | `git status --porcelain -- contract` must be empty. `build` has already re-emitted the schema files over the committed ones, so a modified file is a schema whose source moved without its file and an untracked file is a schema never committed; the gate names them. |
| `bun run test` | `vitest run` over `src/**/*.test.ts`. |
| `bun run test:coverage` | The same suite under v8 coverage, with a 100% floor on statements, branches, functions and lines over `src/`. |
| `bun run ci` | `check`, then `test:coverage`. The one target the pipeline names; run it before opening a pull request. |

`check` begins with `build` because the type check reads `dist/`: the suite imports the package under its own name, which resolves through the `exports` map into `dist/`, and `check:ts` resolves that import the same way. `check` is therefore green on a fresh clone, `ci` builds once, and `test` on a clean tree needs a `build` or a `check` before it.

`check:leakage` refuses any file a commit from this tree would contain that encodes a home path, a local account name, a machine name, a personal e-mail address, a tracker identifier, a decision-record or ruling identifier, a session code, a standards-corpus reference or a path into a planning repository; a word that places this code in relation to some other code or marks it as unfinished; any markdown paragraph broken across lines; and any root entry, hidden directory or capitalised document the gate does not declare. Its identity patterns are derived at runtime, so the gate carries no personal data; its path rules are inventories of what the repository is made of, so adding a root file means declaring it in `scripts/check-leakage.ts` in the same commit. The gate proves itself before it scans: every rule is first run against an input built to violate it, and the gate exits non-zero if any rule stays silent, because a gate that has never been seen to fail is not evidence.

`check:structure` holds every file under `src/` to the structure law stated under Boundaries, one clause per module in `scripts/structure/`. It proves itself the same way: every clause is first run against a source built to violate it, and the gate exits non-zero if any clause stays silent.

The pipeline is `.github/workflows/ci.yml`. Its gate job installs with the lockfile frozen and runs `bun run ci`, so what the pipeline enforces is decided in the manifest, not in the workflow. One gate has no local face: a second job runs `gitleaks` over the full commit history, which is why its checkout is `fetch-depth: 0` — a requirement, not an optimisation, since a shallow clone would scan nothing.

## Conventions

- Licence MIT, author `advl`, declared in the manifest and carried in `LICENSE`.
- Every commit is signed. Subjects are Conventional Commits, lowercase, with no scope for a repository-wide concern; bodies say why, never what the diff already shows.
- Pull request titles are Conventional Commits too, and `.github/workflows/pr-lint.yml` enforces it: merges are squash-only and take the title as the subject that lands on main. `.github/PULL_REQUEST_TEMPLATE.md` is the body's shape.
- Branches are `<type>/<slug>`, the type a conventional-commit type matching the subject the merge lands with. Never a tracker identifier.
- Prose flows: markdown and commit bodies use one paragraph per line and are never hard-wrapped, because a wrapped phrase is unfindable by grep and rewraps into diff noise the moment a word changes. Comments are code and wrap by hand at the formatter's line width, like the lines around them. `check:leakage` refuses a markdown paragraph broken across lines.
- Nothing in this repository points outward. No tracker identifier, session code, decision-record identifier or path into another repository, in source, comments, commits or documentation; `check:leakage` refuses each of these shapes. Where a decision has a rationale worth keeping, the rationale is written in full where it applies.
- Committed text describes this code as what it is: never in relation to some other code it stands in for, and never as unfinished. `check:leakage` refuses the words that do either, in source, comments and documentation alike.
- Fixtures use reserved-neutral names: `example.com`, `@example/*`, `ghcr.io/example/…`. Shared fixture data lives in `src/_testing/fixtures.ts` as named constants and pure renderers — never a JSON file — and a refusal test derives its tripping input from a base fixture with one mutation, so that exactly one refusal fires and the assertion names it.
- A comment explains a hazard. Code that reads as what it does carries none.
- Tests are colocated: `<module>.test.ts` beside `<module>.ts`. An `it` names what a caller can observe, never a mechanism; if the implementation were swapped for a different correct one, the sentence still reads as true.
- Coverage is a floor, not a target. Behaviour lands with the tests that pin it, and the fill comes after; a suite aimed straight at the number runs every line and pins nothing, and the number looks identical either way.
- The `@canonical/*` configs and the `library` ruleset are dependencies on purpose. Do not vendor their contents and do not replace them with local copies; a correction upstream has to reach this package rather than being shadowed by a stale local copy.
- The `library` ruleset defaults to a `@canonical/` name prefix and an `LGPL-3.0` licence, neither of which is true here. Both are overridden by flag — `--license MIT --prefix '@aztlan/'` — rather than by a local ruleset file, for the reason above.
- The toolchain is pinned to exact versions, not ranges. A range would let the installed toolchain drift on the next install, and a gate whose verdict depends on the day it was installed is a different gate on every machine.
- Every domain declines with one class, `Refusal` from the contract domain, whose message says what was declined and why; the register's `RegisterRefusal` extends it to carry structured faults. A caller catches one type and maps it to the one exit code `refused` names, so there is one catch arm for exit 2 and not four.
- Node APIs only, and no `Bun` global anywhere under `src/`. The package runs under Node, and nothing declares the `Bun` global, so a reach for it fails the type check here rather than failing where the code executes.
- A budget is set from five measured windows of the entry, each the seconds of its measured phase: `computeP95` takes them to a p95 by nearest rank — sorted ascending, the sample at position ceil(0.95 × n), which for five is the slowest — and `computeBudget` turns the p95 into a budget: rounded to a tenth, times the headroom, rounded up, and never below the floor. The number of windows, the floor and the headroom are read from the register schema's `$defs.limits`, which also names the estimator, nearest rank, that `computeP95` implements; the tenth-rounding is written once in `_roundToTenth`, and the multiplication and the floor are written once in `computeBudget`. Rounded first and multiplied second, so the pair written into a register answers to itself by a rule a reader checks by hand. `rewriteRunBudget` writes the pair into the register text as one replaced inline table, keeps whatever follows it on the line, and parses nothing: the caller that writes the file parses what it wrote, so the rule for a well-formed row has one home and the budget domain depends on nothing above it. What it refuses is the pair it can see would be declined — a p95 that rounds to zero, a class no TOML string carries, a `run_s` that is not an inline table.

## Boundaries

- The published surface is the manifest's `exports` map and nothing beside it. `src/index.ts` is the module behind `.`: a curated barrel that admits values by name, re-exported from the barrels below it. `src/contract.ts` is the module behind `./contract`: the schemas, the exit codes and the contract version, and nothing that runs. `./contract/*.schema.json` maps onto the committed files under `contract/`, so a consumer in another language reads a schema as a file and a TypeScript consumer reads the same schema as an object, from one definition. Nothing else under `src/` is reachable from outside the package.
- `src/` holds a closed set of members: `index.ts`, one entry module per published subpath, `lib/`, `bin/`, `scripts/`, `testing/`, and the `_`-prefixed never-shipped counterpart of any of them. A member of another kind is a decision, not a drop-in. `check:structure` reads the entry modules from the `exports` map, so the two cannot disagree.
- The structure law, which `check:structure` enforces: a folder is named for its subject, never for a property of the code (`utils`, `internal`, `types`, `commands`, the package's own name, a version suffix); an implementation file exports exactly one value, as `export default` on the definition, named after the file, and beyond it only the types of that value's signature; `types.ts` holds types, `constants.ts` holds constants and `fixtures.ts` holds fixture data and pure renderers, all by name and as `const`; every `index.ts` and every entry module is a pure barrel — no imports, no declarations, no `export *`, reaching `./name.js` in its own directory or `./directory/index.js` and nothing deeper, never a `_`-prefixed module or name, re-exporting a sibling's default under the sibling's name and the constants of a sibling `constants.ts` under their own names, because a collection has no default to alias, and, as types only, the types of a sibling `types.ts` under their own names and the signature types a sibling implementation exports beside its default; a file under `bin/` or `scripts/` exports nothing; a module-level constant never captures the environment; a relative specifier ends in `.js`, is never a `#` alias, and leaves its own directory only to land on another directory's `index.js`, never inside a `_`-prefixed one; a module never imports the package under its own name; `@module` appears on barrels only; a name the lib barrel mints and no entry module admits carries `@package` on its definition, and a name an entry module admits carries no such tag, so the definition and the published surface cannot disagree about which side of the boundary a name is on; and a file past 500 lines opens with a comment naming the threshold and why its content is irreducible. Tests are exempt from the export law and the reach rules, not from the rest.
- Inside a domain, siblings import each other by path; across domains, only through the barrel. A `_`-prefixed module or directory is internal to the directory that holds it and is absent from its barrel.
- The domains under `src/lib/` are pure: a module there touches neither the filesystem, the network, the clock, the environment nor a process; it takes text or values, returns values, or throws a typed refusal, and the reading and writing around it belong to the caller. A module that has an effect carries an `@note` naming the effect, and `src/scripts/` is where the effects the build needs live.
- Two TypeScript configurations, not one. `tsconfig.json` covers everything and never emits; `tsconfig.build.json` narrows to what ships — it drops `src/_*` at the top level and every `*.test.ts` — and is the only one that writes `dist/`. A single configuration would have to either type-check less than the repository contains or emit files that must not travel.
- The pipeline names one target, `ci`. A gate that is added to the manifest is enforced without the workflow changing; a gate the workflow named instead could be added to the manifest and never run, with nothing to say so.
- The coverage `exclude` in `vitest.config.ts` holds tests and declaration files and nothing else. A source file is never added to it to avoid writing its tests.

## Gotchas

- `.gitignore` lists no editor or agent tooling. Keep such paths in your global git ignore: a public ignore file that names them publishes the list it is hiding.
- The build's `src/_*` exclusion is anchored at the top level. A `_`-prefixed module deeper in the tree is emitted, and has to be: a shipped module may import it, and `dist/` would otherwise carry a dangling import. Below the top level the `_` prefix marks intent, not shipment.
- Bun runs the scripts, but `tsc` and `vitest` are `#!/usr/bin/env node` executables and run under whatever Node is on PATH; the suite therefore runs under Node, which is the runtime the package is written for. The manifest's `engines` names 22 or later, and the pipeline installs exactly that; locally, an older Node fails in ways that read like a package defect.
- The leakage gate's probes are assembled from parts, never written out: the gate is inside the set it scans, and a literal violation in it would be found by the very scan it exists to prove.
- A module that declares only types has no statements, so v8 records it as 0/0 and it cannot move the percentages. That is why `vitest.config.ts` carves out no `types.ts`: the carve-out would buy nothing except a hole for any runtime value dropped into such a file.
- `biome.json` holds `extends` and `files.includes` and nothing else, because the `library` ruleset admits no other key. Rules come from the shared config; a rule block added here fails `check:webarchitect`, which reads as a lint misconfiguration and is not one.
- `check:structure` scans `src/` only. The gate scripts under `scripts/` follow the same law by convention — one clause per module, each exporting its one function as the anonymous default, the barrel minting the names — and nothing enforces it there.
- `contract/` is excluded from biome by name in `biome.json`, and the exclusion is load-bearing: the emitter's `JSON.stringify(schema, null, 2)` and a trailing newline are the canonical bytes, and a formatter with an opinion of its own would make `check:contract` red on every build. The `*.json` pattern in the same list reaches every depth, which is why the exclusion has to be spelled.
- The emitter resolves `contract/` from the working directory, not from its own location. `bun run` sets the working directory to the repository root, which is what makes `build:contract` land in the right place; the same property is what lets its test point it at a temporary directory instead.
- The probe a measuring entry writes has a schema like the register and the report, and `readProbe` reads its keys, its phase vocabulary and the version it must name from `probeSchema` and the contract, so an entry written in another language and this reader agree from one definition, at the root of the document as much as inside a reading.
- `src/index.test.ts` and `src/contract.test.ts` pin each entry's values through the module namespace and its types through the built declaration file, because a namespace holds values only and a type can leave the surface with neither namespace moving.
- `check:contract` reads git, not the filesystem, so a fresh emission that has not been committed is a failure by design: the schema files are committed in the same commit as the source that changed them, and the gate is red on a tree where they are not.
- The register's order, its duplicate ids and its line numbers come from a scan of the text's header lines, not from the parser's object: a JavaScript object lists integer-like keys first whatever the text says, the parser reports no positions, and it refuses a redefined table before any row can be read. The scan reads lines, not the grammar, so a header-shaped line inside a multi-line string is taken for a table and refused as a row with every column missing — a register never writes one, and the refusal is louder than silence would be. The budget's rebudget holds a copy of the header-line grammar, since the register reads the budget and the budget cannot read the register without a cycle, and a test feeds the same shapes through both and requires them to agree.
- A register without a `[corpus]` header, or with a header that does not name `contract`, is read as written against the version the schema carries as that property's `default` — `"1"`, the version at which the header did not exist — and never as the current version: the day `CONTRACT_VERSION` moves, every headerless register stays on `"1"` and is refused with the same fault as a header naming `"1"`. `_HEADERLESS_VERSION` in the register's constants reads that default, and `_readHeader` takes the version it reads as a parameter so the refusal is watched firing today rather than on that day.
- `corpus` is the header's name and `reports` is the run reports' directory, so neither is an id a row may take; both are reserved in the schema, and a `[corpus]` table written with row columns is refused as one fault naming the reservation.
- The register refuses a row whose budget is below what its p95 sets, and only below: a budget widened by hand is a margin a reviewer sees in the diff, and a budget below the rule is a kill that fires before the measurement says it should. The floor and the headroom the refusal names are read from the schema's limits, never restated, and a test parses what `rewriteRunBudget` wrote.
- The register's patterns for an id, an image and a file are read from the schema, and the file's refusals — absolute, leaving the tree, on more than one line — are reasons for one miss of that pattern, so the parser and a validator over the emitted file never disagree; a test runs the same paths through both. The suffix a file must carry is the runner's rule, not the schema's, and the parser holds a row to the suffix its caller names.
- Every number the parser and the scheduler hold a register to lives in the register schema's `$defs.limits` — the per-tier ceilings, the deadline outside the measured window, the floor, the headroom, the hard-kill multiplier, the number of measured windows a budget is set from and the p95 estimator over them — and `computeP95` and `computeBudget` read the number of windows, the floor and the headroom from there, so an implementation reads them from the file rather than from prose. The version, the exit codes and the kinds that pool are carried the same way, as `$defs.version`, `$defs.exitCodes` and `$defs.pooledKinds`. The header's `contract` and the probe's `contract` are held to `$defs.version` by the schema itself, so a validator over the emitted file refuses a document on another version exactly where the parser does, and the header's carries as its `default` the version a register without one is written against. The release tier is absent from the limits, which reads as unbounded, because a JSON file cannot carry an infinity.
- `parseRegister` takes what the register cannot read for itself as a required `Pipeline`: the tiers the workflow triggers, the tiers it proves and the suffix the runner collects. The register never reads the workflow; a caller that has read it passes what it found, and a caller with no workflow passes empty lists and is refused for every tier the register holds, which is the refusal a register nothing runs deserves.
- Freshness is two numbers the caller measured on one filesystem. `judgeRun` compares the time the report was written to a mark the run made before it started, both as the filesystem the report lives on dates them; a host clock read against a timestamp stored to whole seconds orders wrongly, and where it does, every honest run is refused as one that reported nothing. A run that left no report, a report older than the run and a run in which nothing executed are refusals — `judgeRun` throws a `Refusal`, and `toExitCode` maps it to `refused` — never red verdicts: the exit codes are the contract, and `refused` there means the scheduler declined to judge, which is what each of these is, and none of them can stand in for the sentinel going red. The verdict is never read from an exit code: a code cannot tell a designed assertion failure from a missing binary or a selector that matched nothing, and each of those is a way to report a fact nobody checked. A report in which tests were collected and none executed — every assertion skipped — is refused the same way as one in which nothing was collected, and `readReport` holds the passed count to the passed assertions listed as it holds the failed count to the failed, so that refusal is read from the assertions and cannot be bought off by a count. The summary and the time its report was written reach `judgeRun` as one value, or as `null` when the run left no report: a summary without a date is not a state a run can be in, so the signature does not admit it and no refusal exists for it.
- Parallelism is a property of a row's kind, never a flag. `planTier` pools the kinds in `POOLED_KINDS` — conformance, oracle and determinism, read by the register from the schema's `$defs.pooledKinds` so the partition is one datum in the emitted file and never a literal here — and serializes every other kind and any row that declares `holds`, after the pool drains: a budget measured beside three other containers is not the budget, and a held resource is one another row could contend for. The wall stays one wall-clock number over the whole schedule — `judgeWall` takes the span from the first pooled container's start to the last serial container's end, measured phases only, never the runs summed — so a pool buys headroom under it and never loosens it; a caller wanting a row to run alone changes its kind or its holds, not an option. The plan is the two lists and nothing else; the ceilings are read from `CEILINGS` where they are needed.
