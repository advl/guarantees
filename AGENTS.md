# AGENTS.md

Instructions for whoever works on this repository. Everything here is true at the commit that carries it.

## Commands

`bun run` is the task face: every gate is a script in `package.json`, and the pipeline runs those scripts and nothing else.

| Command | What it does |
|---|---|
| `bun install` | Installs the toolchain. The lockfile is `bun.lock`; the pipeline installs with `--frozen-lockfile`. |
| `bun run build` | `tsc -p tsconfig.build.json` into `dist/`: modules under `dist/esm`, declarations under `dist/types`; then `build:contract`. |
| `bun run build:contract` | `bun src/scripts/emitSchemas.ts`: one `contract/<name>.schema.json` per schema the `contract` domain declares, written as `JSON.stringify(schema, null, 2)` and a newline into `contract/` under the working directory, or into the directory given as the first argument. |
| `bun run install:corpus` | Links this package into `guarantees/node_modules`, which is the whole of what the corpus installs. Run once after a clone, before `check`. |
| `bun run check` | `build`, then `check:biome` (format and lint over `scripts`, `src`, `guarantees`, `vitest.config.ts` and the JSON files outside `contract/` and the corpus's scratch), then `check:ts` (`tsc --noEmit` over everything `tsconfig.json` includes), then `check:corpus` (the same over the corpus, under the same strict profile), then `check:leakage`, then `check:webarchitect` (the manifest, the biome and TypeScript configuration and the licence against the `library` ruleset), then `check:structure`, then `check:contract`. |
| `bun run check:fix` | The formatter and its safe fixes applied, then the type check. |
| `bun run check:contract` | `git status --porcelain -- contract` must be empty. `build` has already re-emitted the schema files over the committed ones, so a modified file is a schema whose source moved without its file and an untracked file is a schema never committed; the gate names them. |
| `bun run g:<name>` | The corpus face, over the corpus under the working directory: `g <id>` runs one entry, `g:tier <tier>` a tier, `g:list` the register, `g:check` the register against the runner and the tier's images, `g:image [name]` builds an image and checks its record against the tree, `g:prove <tier>` a tier's proof, `g:rebudget <id>` a re-measurement written back under `--class <name>` or the class its row already carries, `g:accept <id>` a run and its goldens. Each is `node dist/esm/bin/guarantees.js <subcommand>`, so `bun run build` comes first. |
| `bun run test` | `vitest run` over both projects: `unit`, every `src/**/*.test.ts` outside `src/_testing/integration/`, and `integration`, the files under that directory, run one at a time against the real container engine. `vitest run --project unit` is the suite on a machine without an engine. |
| `bun run test:coverage` | The same suite under v8 coverage, with a 100% floor on statements, branches, functions and lines over `src/`. |
| `bun run ci` | `check`, then `test:coverage`. The one target the pipeline names; run it before opening a pull request. |

`check` begins with `build` because the type check reads `dist/`: the suite imports the package under its own name, which resolves through the `exports` map into `dist/`, and `check:ts` resolves that import the same way. A fresh clone needs `install:corpus` once before `check`, because `check:corpus` type-checks entry files that import the package by name and the corpus resolves it through an install of its own, which is a link this repository writes and never commits. After that `check` is green from the tree alone, `ci` builds once, and `test` on a clean tree needs a `build` or a `check` before it.

`check:leakage` refuses any file a commit from this tree would contain that encodes a home path, a local account name, a machine name, a personal e-mail address, a tracker identifier, a decision-record or ruling identifier, a session code, a standards-corpus reference or a path into a planning repository; a word that places this code in relation to some other code or marks it as unfinished; any markdown paragraph broken across lines; and any root entry, hidden directory or capitalised document the gate does not declare. Its identity patterns are derived at runtime, so the gate carries no personal data; its path rules are inventories of what the repository is made of, so adding a root file means declaring it in `scripts/check-leakage.ts` in the same commit. The gate proves itself before it scans: every rule is first run against an input built to violate it, and the gate exits non-zero if any rule stays silent, because a gate that has never been seen to fail is not evidence.

`check:structure` holds every file under `src/` to the structure law stated under Boundaries, one clause per module in `scripts/structure/`. It proves itself the same way: every clause is first run against a source built to violate it, and the gate exits non-zero if any clause stays silent.

`guarantees/` is this package's own corpus, and it is two artifacts at once: the guarantee layer this package is held to, and the conformance fixture an implementation of the contract in another language reproduces. Its five rows are the five selftests, one of them the sentinel that fails on purpose, and each entry file is a call to a body the package publishes rather than a scan written out there. `.github/workflows/guarantees.yml` runs its pr tier, and that file is the one the must-run rule reads: the tiers its steps trigger and prove are what every command holds the register to, read from the steps and never from the file's bytes, because commenting a step out is how a step is switched off and a scan over the text reads a disabled step as a live one. A condition on a step, or on the job holding it, is the same gesture in one word and is read the same way — what the reader answers is what the steps run unconditionally, so a guarded step leaves its tier looking unscheduled and refused. One gesture stays outside it and no reading of the steps closes it: an `on:` block that never fires. The workflow runs on a hosted runner and builds nothing: the base image is published once by `.github/workflows/image.yml`, is public, and is fetched by whatever machine the job lands on, which is what a row pinning a published digest buys.

The pipeline is `.github/workflows/ci.yml`. Its gate job installs with the lockfile frozen, links the corpus with `bun run install:corpus`, and runs `bun run ci`, so what the pipeline enforces is decided in the manifest and not in the workflow. The link is a step of its own because it writes into the working tree rather than gating anything, and a manifest script that wrote into the tree on every `check` would be a gate with a side effect. One gate has no local face: a second job runs `gitleaks` over the full commit history, which is why its checkout is `fetch-depth: 0` — a requirement, not an optimisation, since a shallow clone would scan nothing.

## Conventions

- Licence MIT, author `advl`, declared in the manifest and carried in `LICENSE`.
- Every commit is signed. Subjects are Conventional Commits, lowercase, with no scope for a repository-wide concern; bodies say why, never what the diff already shows.
- Pull request titles are Conventional Commits too, and `.github/workflows/pr-lint.yml` enforces it: merges are squash-only and take the title as the subject that lands on main. `.github/PULL_REQUEST_TEMPLATE.md` is the body's shape.
- Branches are `<type>/<slug>`, the type a conventional-commit type matching the subject the merge lands with. Never a tracker identifier.
- Prose flows: markdown and commit bodies use one paragraph per line and are never hard-wrapped, because a wrapped phrase is unfindable by grep and rewraps into diff noise the moment a word changes. Comments are code and wrap by hand at the formatter's line width, like the lines around them. `check:leakage` refuses a markdown paragraph broken across lines.
- Nothing in this repository points outward. No tracker identifier, session code, decision-record identifier or path into another repository, in source, comments, commits or documentation; `check:leakage` refuses each of these shapes. Where a decision has a rationale worth keeping, the rationale is written in full where it applies.
- Committed text describes this code as what it is: never in relation to some other code it stands in for, and never as unfinished. `check:leakage` refuses the words that do either, in source, comments and documentation alike.
- Fixtures use reserved-neutral names: `example.com`, `@example/*`, `ghcr.io/example/…`. Shared fixture data lives in `src/_testing/fixtures.ts` as named constants and pure renderers — never a JSON file — and a refusal test derives its tripping input from a base fixture with one mutation, so that exactly one refusal fires and the assertion names it.
- A comment explains a hazard. Code that reads as what it does carries none.
- Tests are colocated: `<module>.test.ts` beside `<module>.ts`. An `it` names what a caller can observe, never a mechanism; if the implementation were swapped for a different correct one, the sentence still reads as true.
- Coverage is a floor, not a target. Behaviour lands with the tests that pin it, and the fill comes after; a suite aimed straight at the number runs every line and pins nothing, and the number looks identical either way.
- The `@canonical/*` configs and the `library` ruleset are dependencies on purpose. Do not vendor their contents and do not replace them with local copies; a correction upstream has to reach this package rather than being shadowed by a stale local copy.
- The `library` ruleset defaults to a `@canonical/` name prefix and an `LGPL-3.0` licence, neither of which is true here. Both are overridden by flag — `--license MIT --prefix '@aztlan/'` — rather than by a local ruleset file, for the reason above.
- The toolchain is pinned to exact versions, not ranges. A range would let the installed toolchain drift on the next install, and a gate whose verdict depends on the day it was installed is a different gate on every machine. The one range is the runner's peer dependency, `vitest` at `^4`: a corpus runs its entries under its own copy of the runner, and a second copy inside this package would be the version skew the image exists to prevent. The exact version stays in `devDependencies`, which is the copy this repository's own suite runs under.
- Every domain declines with one class, `Refusal` from the contract domain, whose message says what was declined and why; the register's `RegisterRefusal` extends it to carry structured faults. A caller catches one type and maps it to the one exit code `refused` names, so there is one catch arm for exit 2 and not four.
- The corpus layout is spelled once, in `src/lib/runner/constants.ts`: a run masks `INSTALL_DIR` under the workspace, the toolchain stamp walks the same name to find which install answered for a module, and the layering scan skips it along with `WORK_DIR`. A mask that stopped covering what the stamp walks would report a corpus in order over a toolchain nobody chose, so the three read one constant.
- The container engine is spelled once, as `ENGINE` in `src/lib/run/constants.ts`. Every other site — source, tests, the integration suite — reaches it through `ENGINE` or through the `binary` of a probed `Engine`, so the day another engine with the same command surface is admitted, one line moves. Nothing mechanical enforces this; a grep for the literal outside that file is a review step.
- Node APIs only, and no `Bun` global anywhere under `src/`. The package runs under Node, and nothing declares the `Bun` global, so a reach for it fails the type check here rather than failing where the code executes.
- A budget is set from five measured windows of the entry, each the seconds of its measured phase: `computeP95` takes them to a p95 by nearest rank — sorted ascending, the sample at position ceil(0.95 × n), which for five is the slowest — and `computeBudget` turns the p95 into a budget: rounded to a tenth, times the headroom, rounded up, and never below the floor. The number of windows, the floor and the headroom are read from the register schema's `$defs.limits`, which also names the estimator, nearest rank, that `computeP95` implements; the tenth-rounding is written once in `_roundToTenth`, and the multiplication and the floor are written once in `computeBudget`. Rounded first and multiplied second, so the pair written into a register answers to itself by a rule a reader checks by hand. `rewriteRunBudget` writes the pair into the register text as one replaced inline table, keeps whatever follows it on the line, and parses nothing: the caller that writes the file parses what it wrote, so the rule for a well-formed row has one home and the budget domain depends on nothing above it. What it refuses is the pair it can see would be declined — a p95 that rounds to zero, a class no TOML string carries, a `run_s` that is not an inline table.

## Boundaries

- The `corpus` domain is where a command finds what it is about: `CORPUS_DIR`, `REGISTER_FILE` and `WORKFLOW_FILE` are the layout, and `locateCorpus` answers the corpus root, the repository above it, the register and the workflow, refusing a directory with no register in it and a repository with no workflow. Both files are checked there rather than at their readers, because every command needs both and a file that is not there surfaces otherwise as a reader's own fault at exit `red`, which says a guarantee failed about a run in which none was scheduled. The workflow's path is a constant so that a corpus and its pipeline are found by one rule, and `--workflow` overrides it for a repository whose pipeline is somewhere else.
- The base image lives in this repository, under `images/ts/`: a `Containerfile` with both bases pinned by digest, and the `package.json` and `bun.lock` it installs the toolchain from at the image's root. It is built and pushed by `.github/workflows/image.yml` under a name that job owns, it is public, and every row pins the digest that push produced, so a machine running the corpus fetches the image and needs no credential and no build to do it. `buildImage` builds it with the repository root as the context, which is why the Containerfile's `COPY` paths carry the directory, and it builds with `--timestamp 0` and `--omit-history`, which together are what keep the publish answering one digest per definition rather than a new one per run: a layer archive carries the modification time of every file it holds, so two builds minutes apart otherwise hash to two digests, and the build history the engine writes into the image configuration carries the throwaway name it mints for a stage it materialises, which has a random component and lands on whichever step the engine is committing, so two builds on one machine otherwise answer two digests — most often when another build is running beside them. What no flag buys is reproduction across machines: a layer is an archive of a filesystem rather than the filesystem, one engine version building this definition in two environments answered two digests with every file inside byte-identical, and two versions of the build toolchain emit different image configurations from identical files. So a digest is not something a machine reproduces; it is something one machine publishes and every other machine fetches. `hashImageInputs` hashes every file under the directory except `pinned.toml`, path before bytes, and that hash — over files, needing no engine and no build — is what says whether the definition changed, which is the one claim about the image every machine can make. `resolveImage` searches local storage by digest, whatever the tag, before it pulls, so a machine that already holds the image runs against what it has. The record beside the definition carries the digest and that hash and nothing else; no engine version decides anything, because nobody reproduces the digest. `judgePinned` is the whole rule — a green where the definition still hashes to what the record carries, a red where it does not, and a refusal where there is no record, since the digest is a fact about a push and a build here cannot supply one anybody can fetch. Nothing writes the record: the publishing job prints the digest it pushed and the hash beside it, and a reader copies both into `pinned.toml` and into every row.
- The published surface is the manifest's `exports` map and nothing beside it. `src/index.ts` is the module behind `.`: a curated barrel that admits values by name, re-exported from the barrels below it. A name is admitted because a consumer needs it and not because a domain has it, and it is admitted on the entry point of the consumer that needs it: what only a corpus reaches for is published behind `./selftest` and never on the root, so the root stays the surface an embedder of the scheduler reads. `src/contract.ts` is the module behind `./contract`: the schemas, the exit codes and the contract version, and nothing of its own that runs. `src/vitest.ts` is the module behind `./vitest`: `defineCorpusConfig`, the runner configuration a corpus's own `vitest.config.ts` hands to the runner, and nothing else. `src/selftest.ts` is the module behind `./selftest`: the five bodies a corpus imports rather than re-authors, and the three facts a corpus builds their arguments from — `COLLECTS` and `readPipeline`, without which a corpus cannot parse its register the way the scheduler does, and `listTierImages`, which is what registers one toolchain stamp per image a tier names rather than leaving every corpus to filter the register itself. `./contract/*.schema.json` maps onto the committed files under `contract/`, so a consumer in another language reads a schema as a file and a TypeScript consumer reads the same schema as an object, from one definition. Nothing else under `src/` is reachable from outside the package.
- `src/` holds a closed set of members: `index.ts`, one entry module per published subpath, `lib/`, `bin/`, `scripts/`, `testing/`, and the `_`-prefixed never-shipped counterpart of any of them. A member of another kind is a decision, not a drop-in. `check:structure` reads the entry modules from the `exports` map, so the two cannot disagree.
- The structure law, which `check:structure` enforces: a folder is named for its subject, never for a property of the code (`utils`, `internal`, `types`, `commands`, the package's own name, a version suffix); an implementation file exports exactly one value, as `export default` on the definition, named after the file, and beyond it only the types of that value's signature; `types.ts` holds types, `constants.ts` holds constants and `fixtures.ts` holds fixture data and pure renderers, all by name and as `const`; every `index.ts` and every entry module is a pure barrel — no imports, no declarations, no `export *`, reaching `./name.js` in its own directory or `./directory/index.js` and nothing deeper, never a `_`-prefixed module or name, re-exporting a sibling's default under the sibling's name and the constants of a sibling `constants.ts` under their own names, because a collection has no default to alias, and, as types only, the types of a sibling `types.ts` under their own names and the signature types a sibling implementation exports beside its default; a file under `bin/` or `scripts/` exports nothing; a module-level constant never captures the environment; a relative specifier ends in `.js`, is never a `#` alias, and leaves its own directory only to land on another directory's `index.js`, never inside a `_`-prefixed one; a module never imports the package under its own name; `@module` appears on barrels only; a name the lib barrel mints and no entry module admits carries `@package` on its definition, and a name an entry module admits carries no such tag, so the definition and the published surface cannot disagree about which side of the boundary a name is on; and a file past 500 lines opens with a comment naming the threshold and why its content is irreducible. Tests are exempt from the export law and the reach rules, not from the rest.
- Inside a domain, siblings import each other by path; across domains, only through the barrel. A `_`-prefixed module or directory is internal to the directory that holds it and is absent from its barrel.
- The deciding domains under `src/lib/` — `register`, `schedule`, `verdict`, `budget`, `contract` — are pure: a module there touches neither the filesystem, the network, the clock, the environment nor a process; it takes text or values, returns values, or throws a typed refusal, and the reading and writing around it belong to the caller. The `process` domain is the one process boundary: `spawnProcess` is the only module under `src/lib/` that reaches `node:child_process`, and every impure module that runs a host process — the engine's client in `run` and `image`, the corpus's own runner in `listCollected`, the task face a teardown recipe runs on — takes a `spawn: Spawn` defaulting to it, so a unit test hands in a fake that records the argv and answers as scripted, and the integration suite hands in nothing and runs the real engine. The `runner` domain is pure but for `listCollected`, and it is where the corpus layout is spelled — `WORKSPACE`, `WORK_DIR`, `REPORTS_DIR`, `REPORT_FILE` — because the runner is configured to collect nothing under `.work` and a run mounts an entry's subdirectory of it writable, and the two agree by reading one constant; `run` imports them from there. The `run` domain is where containers are started. `describeRun` is pure and is the shape of a run as data — the container's name, its two labels, its mounts, its masks, its working directory, whether it has a network, and its deadline — so the shape is asserted without a container and `runEntry` is the only place one is started; it refuses a relative root before the engine sees it, because a relative host path in a bind mount is a named volume, a malformed name or a path that moves with the working directory, and none of those is the repository.
- The lifecycle of an entry is `runEntry`, and it is one function. The previous run's lifted report is forgotten first, so a run that stops early never leaves an older report standing under its name; the work directory is cleared before the build phase, because an interrupted earlier run is not a path the teardown controls; each build recipe runs in its own container, network on, outside the measured window; the freshness marker is written; the measured run starts with the network off unless the row says `image-net`, under the hard kill at the kill multiplier times the budget; the verdict is judged from the report and the marker, never from an exit code; and `tearDown` runs on every path out — green, red, refused and killed alike — removing every container of the entry by its labels, running the row's teardown recipes on the host task face from the repository root, lifting the report to `.work/reports/<id>.json` and the files under `.work/<id>/lift/` to `.work/reports/<id>/`, both dated as the run wrote them, and removing `.work/<id>`. The report is lifted only when `runEntry` says a verdict was judged from it: a runner writes its report before its own teardown hooks finish, so a container killed at its deadline may leave a passing report beside a red verdict, and a report the reader refused is the account of no verdict; either, lifted under the run's name, would be read as one. The engine's own exit code beside no report, in either phase, is a refusal naming the engine rather than the runner, and it still decides no verdict. Its faults are never lost: they turn a verdict red and are carried in the refusal thrown after a run that already failed. `seconds` is the measured phase alone, which is what a budget is set from, and its unit test makes the build slow so a window that opened before the build reads as longer than the build took.
- `src/bin/guarantees.ts` is the executable, and every subcommand is a composition ending in one exit code. It parses arguments and composes; it walks no tree, starts no process directly, reads no report and holds no judgement — every verdict it prints goes through one `say`, which is `toExitCode` and a line. Two decisions are made there that no domain makes for it: which corpus a command is about, composing `locateCorpus` with what `--corpus` gave; and that the register is read against the workflow at all, composing `readPipeline` into `parseRegister`, so a tier no job runs is refused on every command rather than by an assertion inside that tier which cannot observe its own absence. `check` takes `judgeCorpus`, which asks both directions of the bijection through the same two finders the row that pins it calls, so the pre-flight and the entry answer one question the same way; a tier's many codes reduce through `worstCode`, by name and never by arithmetic over the numbers; and `rebudget` takes `judgeBudget` and writes only what the register would carry and only from windows every one of which measured the entry doing what its row promises, since a pair past the tier's ceiling is one every later command refuses and a window measured by a run that did not is not a measurement of the entry. It reaches the domains it composes one at a time and never through the lib barrel, because that barrel mints the selftest bodies and every one of them imports the runner at load: through it, `guarantees list` over five rows would start the runner to print them. It sets `process.exitCode` and never calls `process.exit`, which is both the correctness rule — an exit does not unwind, and a teardown still has to run — and what lets its own test import the module and drive every arm.
- A tier's pool runs in slices of the machine's concurrency, and each row answers its own code rather than the slice racing to the first rejection: every row of a slice tore its own entry down and has something to report. A worker queue would idle less when one row in a slice is slow; a slice holds no scheduling judgement and the wall is judged once over the whole schedule either way, so if a queue is ever wanted it belongs beside `planTier` in `schedule` and never in the executable.
- A tier's proof is `proveTier`, and it is per tier because that is what a proof is about. Every tier runs its row designed to fail and requires it red, which shows the runner and the scheduler can report a failure at all; the tier holding the bijection additionally installs a test file no row claims, runs that row, and requires the one named assertion among the failed — because a scan that sees nothing compares two empty lists and stays green while the sentinel beside it stays red on schedule. The assertion is required by the title the contract publishes, so the body that carries it and the proof that names it read one datum and neither of them owns it, under the id the suite is opened by and never under the row's selector, which a corpus is free to write as a prefix selecting one assertion of that suite, and it is read from the LIFTED report and never from a count line or an exit code: a count accepts any assertion in the file, and a register that no longer parses, an image that will not resolve and a hard kill all exit non-zero with the scan never having run. The report has to be this run's, and freshness is the mark the run made against the date the report carries, both from the corpus's own filesystem — a teardown recipe runs between the read a verdict was judged from and the copy that outlives the work directory, so those are two reads of one file and the second is the one a proof believes. The tree is restored on every path out, the throw included, and the rigged run's own lifted evidence goes with it.
- The selftests ship as bodies and not as files, because the bijection scans the consumer's own tree and has to find itself in it. Every finding is a list compared against an empty one, and two empty lists compare equal, so each finding goes through `_requireNothingFound`, which registers two assertions under two titles: how much was looked at, and what was found, each with the sentence a reader meets when it fires. Two titles and not one, because a tier's proof requires one of them among the failed by name: under a shared title a scan that read nothing fails the title the proof looks for, and the proof reports the planted file found by a scan that never saw it — the vacuity the pair exists to separate, one level up. That is also what makes the wiring from a finder to an assertion watched failing rather than only watched passing, since a shell run against a fixture that agrees with itself is green whichever of a finder's lists it was handed. Each body opens one suite named by its caller — the row's id, so the row's selector finds it — and takes the corpus's own facts as arguments rather than discovering them, since a body that guessed where it stood would assert something about a tree it inferred. Which facts those are is the line the arguments are drawn on: where a run covers the repository's own install is the run's fact, so the toolchain stamp defaults to it and a corpus asked to state it could only retype a path it cannot import — and a wrong one naming an empty directory passes the assertion the mask exists to make; what a corpus pins and does not build is the corpus's fact, so the image tie takes it, and without it a corpus deriving no image of its own is red in all three directions for having nothing. Each is a short registration shell over an `_`-prefixed pure finder, which is what lets both directions of every finding be asserted without a runner: the finders get table-driven tests, and each shell is run un-skipped against a fixture that agrees with itself. A fixture that agrees with itself cannot watch the wiring, so each shell is additionally registered under a replaced runner through `captureRegistration`, against a fixture broken in exactly one direction, and the title that direction belongs to is required to fail while the others hold. `describeCanFail` is the exception and the reason for the split — its one assertion is designed to fail, so it is registered inside a skipped suite, where the registration runs at collection and the assertion does not, and what the assertion does is watched separately over `_failOnPurpose`. `describeLayering` compares resolved paths rather than name segments, because this package's own name ends in the word its corpus directory is called, and a segment scan reports every import of it as a trespass.
- A golden changes by one path, `acceptGolden`, and never by a hand that edits the file. A golden has to be generated inside the image the entry runs in, because one written by whatever toolchain a developer happens to have is a claim about that machine, and the entry's `lift/` directory is its only route out of a container teardown empties on every path. So an accept is a run and then a copy of what that run lifted, and it answers what it added, replaced, left unchanged and no longer generates — the last left standing, because a golden a row stopped generating is a question for whoever reads the diff. It does not require the run to be green: the first accept of any golden runs red because the golden is not there yet, and the accept after an intended change runs red because the surface moved, so requiring green would make the command unable to do the one thing it is for. A MISSING golden is the ENTRY's failure and never the accept's — the entry compares and goes red — and the accept refuses a run that lifted nothing and a lifted file older than the run, which are the two ways an earlier tree's claim could be committed under this run's name.
- A kill is a red verdict and a failed build is a refusal. A container removed at its deadline breached the budget, which is the fact the kill measures, so the verdict is red naming the multiplier and the budget and no report is read from a container removed mid-run. A build recipe that fails, hangs or leaves nothing under `.work/<id>` means the measured phase never started: no assertion executed and there is nothing to judge, which is what `refused` means. Both exit non-zero.
- `reapStale` runs before anything of a run has started, and only then. It takes the repository root and hashes the checkout label itself, as `runEntry` does from the same root, so the label it filters by is the label the run's containers carry and no caller can hand in one that matches nothing; `RunContext` carries no label for the same reason. The filter is the checkout, which this run's own containers also carry, so a reap mid-tier would remove the tier's own entries: it is a caller's first engine call, before any `runEntry` of the same root. This package ships no such caller; the integration files are the callers, and each reaps its own corpus first. A module that has an effect carries an `@note` naming the effect and why, module-private helpers included, and `src/scripts/` is where the effects the build needs live. The `image` domain reads the image's directory and spawns the engine; `readPinned` alone is pure.
- The runner is asked, never second-guessed. `listCollected` runs the corpus's own copy of the runner in its list mode and answers with the files it would collect, relative to the corpus root; `findUnclaimedFiles`, `findUncollectedRows` and the `judgeCorpus` over them sit in the same domain, beside the answer they consume, so a command reaches the question without loading a module that imports the runner to register a suite; a corpus that does not resolve the runner is refused by name, and this package's copy never stands in, because a list produced by another runner is a claim about another corpus. `renderEntryCommand` names the runner's binary at the image's root, `/node_modules/.bin/vitest`, where the repository's bind mount cannot cover it, and hands the row's `select` to the runner's filter escaped and anchored to the start of the full title at a word boundary, never as a pattern: the runner's filter is a regular expression over the suite titles and the test title joined by single spaces, and a selector passed through as written would let `corpus-bijection (every row)` select `corpus-bijection every row` and judge an assertion the register never named. The register schema's description of `select` says the same, so a register author and the runner agree on what a selector is.
- Two TypeScript configurations, not one. `tsconfig.json` covers everything and never emits; `tsconfig.build.json` narrows to what ships — it drops `src/_*` at the top level and every `*.test.ts` — and is the only one that writes `dist/`. A single configuration would have to either type-check less than the repository contains or emit files that must not travel.
- The pipeline names one target, `ci`. A gate that is added to the manifest is enforced without the workflow changing; a gate the workflow named instead could be added to the manifest and never run, with nothing to say so.
- The coverage `exclude` in `vitest.config.ts` holds tests and declaration files and nothing else. A source file is never added to it to avoid writing its tests.

## Gotchas

- `.gitignore` lists no editor or agent tooling. Keep such paths in your global git ignore: a public ignore file that names them publishes the list it is hiding.
- The build's `src/_*` exclusion is anchored at the top level. A `_`-prefixed module deeper in the tree is emitted, and has to be: a shipped module may import it, and `dist/` would otherwise carry a dangling import. Below the top level the `_` prefix marks intent, not shipment.
- Bun runs the scripts, but `tsc` and `vitest` are `#!/usr/bin/env node` executables and run under whatever Node is on PATH; the suite therefore runs under Node, which is the runtime the package is written for. The manifest's `engines` names 22 or later, and the pipeline installs exactly that; locally, an older Node fails in ways that read like a package defect.
- The leakage gate's probes are assembled from parts, never written out: the gate is inside the set it scans, and a literal violation in it would be found by the very scan it exists to prove.
- The integration project's global setup, `src/_testing/prepareEngine.ts`, probes the engine, builds the base image under a tag of its own process — `localhost/guarantees-ts:integration-<pid>` — pulls one small image by digest, hands the engine and the built image to the files through `provide`, and when the suite ends removes the tag it minted and the small image only if the setup was what pulled it. The image is handed on by its ID, never by the tag: the store is shared by every process on the machine, and a second suite building from another checkout would repoint a fixed tag and remove it from under this one mid-suite, whereas the ID names this build and nothing else. The small image reaches the files as its digest-pinned reference, which the engine resolves locally and pulls again if a file removed it, never as a store ID a sibling file can invalidate. Removing the built image evicts its layer cache, so every `bun run test` rebuilds the base image — a minute or three, most of it the toolchain install inside the build — and that is the price of leaving the image store as the suite found it. The setup runs in the runner's main process, where coverage collects nothing, so it has a unit test of its own with a fake project and a fake spawn, and both live beside the other test support under `src/_testing/` rather than in the integration directory, so the test runs under the `unit` project on a machine without an engine.
- `makeCorpus`, under `src/_testing/`, writes a temporary repository with a `guarantees/` corpus, and every corpus it makes is a checkout of its own: its label is the hash of its directory, so a sweep by that label touches nothing another file started. A unit test takes a fresh temp directory. An integration file names its corpus, and the root is then a fixed place under the temp directory keyed by this package's own checkout and that name, recreated empty — the same label on every run of the file from this checkout, so what a run interrupted mid-file left running is exactly what the next run's reap finds. Every integration file therefore opens with `reapStale` on its own corpus, before it starts anything, and filters its own listings by the corpus label beside the entry label, since another process may be running the same fixture entries. Two checkouts of this package on one machine key to different roots, tags and labels and never touch each other; two suites from one checkout at once share its coverage directory and its fixture roots, and are not a supported way to run it. Rows there are plain objects, never parsed from a register, because the register's budget floor binds registers and a fixture entry needs a budget of a second.
- The corpus installs the package and nothing else, and it is a link rather than an install. Installing the parent by path brings the parent's own dependencies into the corpus's install, and every one of them is a package the image already carries at a pinned version — so the corpus would resolve its toolchain from the checkout, which is the fault the mask exists to refuse, and the toolchain guarantee would go red on the arrangement meant to support it. The link is relative, because the repository is mounted at another path inside the image and an absolute one would point outside the mount.
- The runner writes while it reads a corpus's configuration, into a directory beside the corpus's install, so a corpus mounted read-only cannot be configured at all: the runner stops before collecting anything and every entry of the tier reports that it left no report. A run therefore gives it that one writable path, spelled as `RUNNER_SCRATCH` beside the rest of the corpus layout. The day the runner writes somewhere else instead, a tier says so at once rather than quietly running unconfigured.
- A run masks the repository's own install, and the mask is a volume with no host side rather than a tmpfs. The repository is bind-mounted read-only at `/workspace` and its own hoisted `node_modules` sits directly above the corpus on the runtime's upward resolution path, so without a mask every entry resolves whatever the machine last installed and the image is decorative. A tmpfs cannot do it: the engine lays every tmpfs down before the bind mounts, so one at a path under the workspace is covered by the workspace bind itself and hides nothing while appearing in the container's mount table. A volume with no host side is created empty for the container alone, which is also why `_removeContainer` passes `--volumes`: the engine drops such a volume with a container that exits on its own and keeps it when the container is removed by name. The corpus's own install is deliberately left visible, because that is where a corpus keeps the package whose selftest bodies its entries import.
- The engine's `untag` with one argument strips every name from the image. The integration suite tags the base image under a second name to prove resolution by digest, and untags by naming the tag twice, because the one-argument form left the built image nameless mid-suite.
- The engine is probed once per process, by the caller, and never inside a run: `probeEngine` refuses a machine without the engine by name, and its reader is `runEntry` through its context's `engine`. There is no fallback to another engine and no path that starts a container without a probe having answered.
- Every engine call has a deadline, and the deadline on a container run is met by removing the container — `rm --force --time 0 --ignore <name>` — never by a signal to the client: killing the client detaches it and leaves the container running, holding its mounts and writing for as long as it lives. `spawnProcess` awaits the removal and only afterwards signals a client that is still alive, which is tidy-up of a process already done, or the last resort when the engine did not answer the removal.
- A listing that fails or is killed at its deadline prints nothing, and nothing is what a clean machine prints. `_listLabelled` therefore answers whether the engine answered beside the names, and every caller judges the answer rather than the list: an engine that will not say what is running is not a clean machine.
- Every container carries two labels, read from the contract's label schema so a reader of `label.schema.json` filters by the same keys: `corpus`, the first twelve hex digits of a hash of the repository root's absolute path, and `entry`, the row's id. The checkout is in the label because two checkouts of one repository — a main tree and a worktree, two jobs on a runner — share no work directory and no register, and the label is what keeps a reap from tearing down the other's entry mid-measurement. `hashCheckout` refuses a relative path, since two working directories would hash one checkout twice.
- An interrupt is not a path the lifecycle controls. What an interrupted run leaves is a container still executing, holding its mounts and writing for as long as it lives, and a report the next attempt would otherwise read; `reapStale` removes the container by the checkout label before the next run and refuses when the engine does not answer, and `runEntry` clears `.work/<id>` and the lifted report before it starts. A second checkout of the same repository hashes to another label and is never touched.
- The runner writes its report to a path relative to the corpus directory, `.work/<id>/report.json`, because that directory is the measured run's working directory inside the container; the host reads the same file through the work directory's mount.
- `defineCorpusConfig` runs files one at a time and reports no coverage, and both are decisions rather than defaults. Entries are scheduled by the package, one container per row; a second scheduler inside the runner would put two measured windows in one container, where neither is the budget its row was measured for. Coverage is a property of a suite colocated with the code it covers, and a number over a corpus describes the corpus's own control flow and nothing about what its entries pin. Every exclusion is shaped `**/<dir>/**` because the bijection's scan skips a directory by name wherever its walk meets one, and an exclusion anchored at the root would keep collecting a nested `fixtures/` the scan steps over; the `.work` exclusion is spelled from `WORK_DIR`, and the real-runner test in `listCollected.test.ts` runs a corpus whose `vitest.config.ts` imports `defineCorpusConfig` through the built `./vitest` entry, with a nested `fixtures/` in it, so the shipped configuration and not a copy of it is what the list is produced under. An override's `test` key replaces the base's key of the same name whole: a list merged by concatenation could widen `include` and never narrow it.
- A module that declares only types has no statements, so v8 records it as 0/0 and it cannot move the percentages. That is why `vitest.config.ts` carves out no `types.ts`: the carve-out would buy nothing except a hole for any runtime value dropped into such a file.
- `biome.json` holds `extends` and `files.includes` and nothing else, because the `library` ruleset admits no other key. Rules come from the shared config; a rule block added here fails `check:webarchitect`, which reads as a lint misconfiguration and is not one.
- `check:structure` scans `src/` only. The gate scripts under `scripts/` follow the same law by convention — one clause per module, each exporting its one function as the anonymous default, the barrel minting the names — and nothing enforces it there.
- `contract/` is excluded from biome by name in `biome.json`, and the exclusion is load-bearing: the emitter's `JSON.stringify(schema, null, 2)` and a trailing newline are the canonical bytes, and a formatter with an opinion of its own would make `check:contract` red on every build. The `*.json` pattern in the same list reaches every depth, which is why the exclusion has to be spelled.
- The emitter resolves `contract/` from the working directory, not from its own location. `bun run` sets the working directory to the repository root, which is what makes `build:contract` land in the right place; the same property is what lets its test point it at a temporary directory instead.
- The probe a measuring entry writes has a schema like the register and the report, and `readProbe` reads its keys, its phase vocabulary and the version it must name from `probeSchema` and the contract, so an entry written in another language and this reader agree from one definition, at the root of the document as much as inside a reading.
- `src/index.test.ts`, `src/contract.test.ts` and `src/selftest.test.ts` pin each entry's values through the module namespace and its types through the built declaration file, because a namespace holds values only and a type can leave the surface with neither namespace moving.
- Importing any entry loads the runner, and the binary does not. The barrel-reach rule leaves `src/selftest.ts` able to name `./lib/index.js` and nothing deeper, so the lib barrel mints the selftest bodies, and those import `vitest` — which every entry module reaches transitively, `./contract` and `./vitest` as much as the root, since all four re-export from the one barrel. `vitest` is a declared peer, so it resolves wherever the package is installed to run a corpus, and what it costs is the load: a program embedding only the scheduler, and a consumer reading only the schemas, both pay it. `src/bin/guarantees.ts` is not an entry module and reaches the domain barrels directly, so nothing it composes loads the runner — a claim no run of the binary can make about itself, so its own test walks the import graph from it over the source and requires no module in it to import the runner; the two finders behind the bijection are in `runner` beside the answer they consume, for the same reason and because the pre-flight and the entry have to ask one question. A consumer in another language reads `./contract/*.schema.json` as files and pays nothing. The alternatives are worse: passing `describe` and `it` in as parameters puts the runner in every body's signature, and a lazy require of an ESM-only package is not one.
- `check:contract` reads git, not the filesystem, so a fresh emission that has not been committed is a failure by design: the schema files are committed in the same commit as the source that changed them, and the gate is red on a tree where they are not.
- The register's order, its duplicate ids and its line numbers come from a scan of the text's header lines, not from the parser's object: a JavaScript object lists integer-like keys first whatever the text says, the parser reports no positions, and it refuses a redefined table before any row can be read. The scan reads lines, not the grammar, so a header-shaped line inside a multi-line string is taken for a table and refused as a row with every column missing — a register never writes one, and the refusal is louder than silence would be. The budget's rebudget holds a copy of the header-line grammar, since the register reads the budget and the budget cannot read the register without a cycle, and a test feeds the same shapes through both and requires them to agree.
- A register without a `[corpus]` header, or with a header that does not name `contract`, is read as written against the version the schema carries as that property's `default` — `"1"`, the version at which the header did not exist — and never as the current version: the day `CONTRACT_VERSION` moves, every headerless register stays on `"1"` and is refused with the same fault as a header naming `"1"`. `_HEADERLESS_VERSION` in the register's constants reads that default, and `_readHeader` takes the version it reads as a parameter so the refusal is watched firing today rather than on that day.
- `corpus` is the header's name and `reports` is the run reports' directory, so neither is an id a row may take; both are reserved in the schema, and a `[corpus]` table written with row columns is refused as one fault naming the reservation.
- A register is refused when it holds rows and none of them is the row a proof rigs, for the reason a tier is refused when none of its rows is designed to fail: the bijection's two directions compare two lists, a scan that looked nowhere compares two empty ones and reads exactly like a corpus in order, and only a run of that row against a file no row claims has ever shown it able to find anything. The id is `$defs.prove.bijectionId` in the register schema, beside the id a proof installs its file under and the title it requires among the failed, so all three are data an implementation in another language reads rather than three literals each of them is trusted to reproduce.
- The register refuses a row whose budget is below what its p95 sets, and only below: a budget widened by hand is a margin a reviewer sees in the diff, and a budget below the rule is a kill that fires before the measurement says it should. The floor and the headroom the refusal names are read from the schema's limits, never restated, and a test parses what `rewriteRunBudget` wrote.
- The register's patterns for an id, an image and a file are read from the schema, and the file's refusals — absolute, leaving the tree, on more than one line — are reasons for one miss of that pattern, so the parser and a validator over the emitted file never disagree; a test runs the same paths through both. The suffix a file must carry is the runner's rule, not the schema's, and the parser holds a row to the suffix its caller names.
- Every number the parser and the scheduler hold a register to lives in the register schema's `$defs.limits` — the per-tier ceilings, the deadline outside the measured window, the floor, the headroom, the hard-kill multiplier, the number of measured windows a budget is set from and the p95 estimator over them — and `computeP95` and `computeBudget` read the number of windows, the floor and the headroom from there, so an implementation reads them from the file rather than from prose. The version, the exit codes and the kinds that pool are carried the same way, as `$defs.version`, `$defs.exitCodes` and `$defs.pooledKinds`. The header's `contract` and the probe's `contract` are held to `$defs.version` by the schema itself, so a validator over the emitted file refuses a document on another version exactly where the parser does, and the header's carries as its `default` the version a register without one is written against. The release tier is absent from the limits, which reads as unbounded, because a JSON file cannot carry an infinity.
- `parseRegister` takes what the register cannot read for itself as a required `Pipeline`: the tiers the workflow triggers, the tiers it proves and the suffix the runner collects. The register never reads the workflow; a caller that has read it passes what it found, and a caller with no workflow passes empty lists and is refused for every tier the register holds, which is the refusal a register nothing runs deserves.
- Freshness is two numbers the caller measured on one filesystem. `judgeRun` compares the time the report was written to a mark the run made before it started, both as the filesystem the report lives on dates them; a host clock read against a timestamp stored to whole seconds orders wrongly, and where it does, every honest run is refused as one that reported nothing. A run that left no report, a report older than the run and a run in which nothing executed are refusals — `judgeRun` throws a `Refusal`, and `toExitCode` maps it to `refused` — never red verdicts: the exit codes are the contract, and `refused` there means the scheduler declined to judge, which is what each of these is, and none of them can stand in for the sentinel going red. The verdict is never read from an exit code: a code cannot tell a designed assertion failure from a missing binary or a selector that matched nothing, and each of those is a way to report a fact nobody checked. A report in which tests were collected and none executed — every assertion skipped — is refused the same way as one in which nothing was collected, and `readReport` holds the passed count to the passed assertions listed as it holds the failed count to the failed, so that refusal is read from the assertions and cannot be bought off by a count. The summary and the time its report was written reach `judgeRun` as one value, or as `null` when the run left no report: a summary without a date is not a state a run can be in, so the signature does not admit it and no refusal exists for it.
- Parallelism is a property of a row's kind, never a flag. `planTier` pools the kinds in `POOLED_KINDS` — conformance, oracle and determinism, read by the register from the schema's `$defs.pooledKinds` so the partition is one datum in the emitted file and never a literal here — and serializes every other kind and any row that declares `holds`, after the pool drains: a budget measured beside three other containers is not the budget, and a held resource is one another row could contend for. The wall stays one wall-clock number over the whole schedule — `judgeWall` takes the span from the first row of the pool starting to the last serial row being torn down, every phase of every row included, never the runs summed and never the measured phases alone, which is what each row's own budget bounds — so a pool buys headroom under it and never loosens it; a caller wanting a row to run alone changes its kind or its holds, not an option. The plan is the two lists and nothing else; the ceilings are read from `CEILINGS` where they are needed. How wide the pool runs is `runPool`, beside the partition it completes rather than in the executable that prints the results, and it settles every row of a slice before raising one that rejected, because a slice racing to the first rejection drops the verdicts beside it and the serial list after it.
